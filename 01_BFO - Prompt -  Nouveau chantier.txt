Projet BlueFox — Nouveau chantier

Nous ouvrons un nouveau chantier sur le dépôt GitHub courant.

1. Commence impérativement par appliquer le protocole projet :

lire 00_AI_PROJECT_RULES.md ;
lire docs/README.txt ;
lire uniquement les documents de référence officiels qu’il désigne ;
identifier le commit GitHub courant et le prendre comme base exclusive ;
ne jamais repartir d’un ancien ZIP, d’un ancien fichier local ou d’une ancienne tentative rejetée ;
auditer les fichiers concernés et leurs interactions avant de proposer une correction.

2. DOCUMENT GAMEPLAY À LIRE AVANT TOUT AUDIT TECHNIQUE

Ce document doit être lu AVANT de proposer une stratégie technique.

Il rassemble les intentions de gameplay retrouvées dans :

* le cahier des charges ;
* la Bible narrative ;
* les documents missionnels ;
* CUO / CUM ;
* les documents techniques ;
* l’historique des validations ;
* nos conversations de développement ;
* les corrections et arbitrages successifs de juillet et août.

Ce document n’est PAS une nouvelle couche moteur.

Il sert uniquement de **référentiel d’intention et de non-régression gameplay**.

### Ordre d’autorité fonctionnelle

Lorsqu’il existe une contradiction :

1. décision gameplay explicite la plus récente de l’utilisateur ;
2. validation directe en jeu par l’utilisateur ;
3. Bible narrative / document fonctionnel récent ;
4. documents officiels du projet ;
5. anciennes traductions CUM/CUO/Bible moteur ;
6. code actuel.

Le code ne définit pas à lui seul l’intention.

3. Première passe uniquement : diagnostic + stratégie

Essaie d’être rapide et ciblé.

Je veux :

l’état exact de la fonctionnalité dans le commit courant ;
ce qui existe déjà et doit être conservé ;
ce qui manque ou a régressé ;
ce qui avait été validé précédemment et mérite d’être récupéré ;
les fichiers réellement concernés ;
les risques de régression ;
une stratégie d’intégration synthétique mais techniquement justifiée.

Ne génère encore aucun correctif à cette étape.

4. IMPORTANT — NE PAS REPRODUIRE LES ERREURS DES CHANTIERS PRÉCÉDENTS

Plusieurs sessions dites de « consolidation », « nettoyage » ou « récupération » ont elles-mêmes produit de nouvelles régressions.

Par conséquent :

### Il est interdit de raisonner ainsi :

> fichier mal propriétaire → on supprime son wrapper → propriétaire officiel restauré → problème réglé.

Avant de retirer ou neutraliser quoi que ce soit, il faut identifier **TOUS les comportements gameplay actuellement transportés par cette couche**.

Même une couche architecturalement mauvaise peut aujourd’hui être la seule à assurer une fonctionnalité validée.

La suppression n’est acceptable qu’après preuve de conservation du comportement.

| ---------------- | ------------------ | ----------- | ------------------ | ------------------- | --------------------------- | ---------------------------- | --------- | --------------------- | ----------------------- | --------- | -------------------------------------------- | ------- |

Le document Gameplay V2 doit fournir la base de cette matrice.

Complète-la avec les références du dépôt et l’historique pertinent lorsque nécessaire.



6. Après ma validation de la stratégie

Tu réalises le correctif en repartant exclusivement des fichiers du commit courant ou de la cible désignée.

Contraintes de livraison :

ne modifier que les fichiers strictement nécessaires ;
conserver toutes les fonctions déjà validées présentes dans ces fichiers ;
aucun fichier avec suffixe de version ajouté pour le patch ;
aucun README parasite ;
aucun .bat, .ps1 ou .patch sauf demande ;
ZIP contenant uniquement les fichiers réellement modifiés ;
vérifier le diff contre le commit de départ ;
effectuer les tests disponibles ;
ne jamais annoncer le correctif comme validé si une partie n’a pas pu être vérifiée.

7. Une fois le correctif validé en jeu

On décide ensemble s’il faut :

le commiter ;
mettre à jour MASTER.md, ARCHITECTURE_TECHNIQUE.md, ROADMAP_TODO.md, DEV_HISTORIQUE.md et les autres références officielles réellement concernées.
